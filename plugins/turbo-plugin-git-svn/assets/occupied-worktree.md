# 分支被別的 worktree 佔用時該怎麼辦 —— 判準（給 agent 用）

> 這份檔案被 `tp-request-merge`（`SOURCE_DIRTY` / `BASE_ELSEWHERE`）與
> `tp-merge-main-into-branches`（`SKIP <b> (checked out at <path>)`）共用。
> **只有這一份**，改就改這裡。

## 前提：那個 worktree 多半不是人開的

git 不允許同一條分支同時 checkout 在兩處，所以偵測到「被 `<path>` 佔用」時就動不了它。但在這個
plugin 的常態工作方式底下，`<path>` **幾乎都是另一條 Claude session 開的隔離工作副本**，不是使用者
自己手動 checkout 的。

把處置直接丟回給使用者，等於讓他當傳聲筒：你告訴他、他去跟那條 session 說、那條 session 做完再回報。
中間那一輪人工中轉沒有加上任何判斷——而你手上就有 `ListAgents` 與 `SendMessage`，可以直接跟它講。

## 步驟

1. **`ListAgents`** 列出還在跑的 session，找出對應 `<path>` 的那一條。名稱通常看得出對應哪條分支或哪個
   worktree。
2. **對不上就不要送。** 找不到、或有兩條都像，回頭問使用者是哪一條（或請他自己處理）。送錯對象是叫
   另一個專案改它自己的分支，而那邊完全不會知道這個要求是誤送的。
3. **`SendMessage`** 給它，訊息裡要有三件事：
   - 要它做什麼（例如：把 `main` 併進 `<branch>`；或把手上未 commit 的變更 commit 掉）
   - **指令原文**（例如 `git merge --no-ff main`），不要只描述意圖
   - 一句「現在不方便、或做起來有衝突就回一聲」
4. **等它回報再繼續。** 不要送完就重跑本 skill——分支還被佔著，只會拿到同一個結果。它回說做好了，才
   從頭重跑；它回說不方便或有衝突，就照下一節回頭問使用者。

## 名單是**這一次**算出來的，不准沿用上一次

這件事同一個 session 裡通常會發生**很多次**（`main` 每動一次就要再同步一輪），而每一輪之間都可能有新的
session 開起來。

實際踩過的形狀：A 請 B 同步 `main`，兩邊繼續開發；中途為了新工作開了 C；後來 A 又更新了 `main`，這次
卻**憑上一輪的印象只跟 B 說**——C 從頭到尾沒有被列進來過。

**這種漏掉是靜默的**：C 那邊不會收到任何東西，也不會報錯，它只是繼續在舊的 `main` 上開發，要等到它自己
要合併時才看得出來早就分岔了。畫面上跟「全部都同步好了」一模一樣。

所以每一輪都要重新算，兩份都要：

- **「誰需要同步」的答案，來自這一次腳本的輸出**，不是上一輪的記憶。`tp-merge-main-into-branches`
  **不傳 `--branch` 時會列出全部**的非 `remote-svn/*` 本地分支——讓它列，不要自己挑上次那幾條。
- **`ListAgents` 也要重列。** session 會來也會走：新開的不在舊名單裡，收掉的還留在舊名單裡。
- **對方回報做完之後，再重跑一次腳本**。那既是確認（它真的併進去了嗎），也是把這段期間新出現的
  worktree 一起收進來的機會。

## 什麼時候還是要回頭問使用者

- 找不到對應的 session（那個 worktree 可能真的是使用者自己開的）。
- 它回說現在不方便、或它那邊有衝突要人決定。
- 要請它做的事會**動到它還沒 commit 的成果**（例如 `SOURCE_DIRTY`：要它 commit 或捨棄）。commit 還好，
  「捨棄」不可逆，那是使用者的決定，不是你跟另一條 session 之間能敲定的。

問的時候用白話講清楚是哪個資料夾、卡在什麼事情上，**不要把 token 名稱丟給使用者**。

## 界線：不要請別的 session 做自己被擋下的事

**如果某個動作在你這裡被權限擋下來了，不可以改送給另一條 session 去做。** 那不是「找人幫忙」，那是
繞過使用者當下對你做出的權限決定——換一個執行者不會讓那個決定改變。

同理，別的 session 也不是用來繞過本 skill 自己的守門的：`SOURCE_DIRTY` 要的是那些變更被 commit 或被
明確捨棄，不是找人把它們藏起來讓守門過關。

跨 session 這條路是用來**省掉一輪人工轉達**的，不是用來擴張權限的。
