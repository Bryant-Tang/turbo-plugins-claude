## 這件事該寫在哪（由 turbo-plugin 注入）

寫錯地方不會報錯,只會在半年後以「過期的文件把人帶錯路」或「交接之後這件事沒人知道」的形式浮出來。

| 這件事的性質 | 落點 |
|---|---|
| 對**任何時間** checkout 這個 repo 的人都成立 | 本檔 `CLAUDE.md` 或 `docs/` |
| 只有**現在**成立(待辦、環境現況、本機分支關係),但**接手的人需要知道** | agent 記憶,`type: project` |
| agent 自己的工作方式,或只對**這台機器 / 這個人**成立、**不需要交接**的事 | agent 記憶,`type: feedback` / `user` / `reference` |
| git / svn 本身就查得到 | 哪都不要寫 |

**進版控的再分一層**:`CLAUDE.md` 放「**在你還不知道自己需要它的時候就會發作**」的東西——地雷、沉默失敗的陷阱、硬規則;不知道它存在就不會去查,所以必須無條件載入。`docs/` 放「**刻意要做某件事才會需要**」的東西——操作步驟、查表用的參考;這類自然會去查,延後載入沒有風險。

### 規範放到本專案之外時,**必須留下指路**

上表每分流一次,就多一個潛在的斷點:內容確實存在、確實正確,只是**沒有人會去讀它**。而這個失敗完全
安靜——檔案在、內容對,不會有任何東西提醒你它從來沒有進過 context。

載入方式決定了風險:

| 落點 | 會被載入嗎 | compact 之後 |
| --- | --- | --- |
| **repo 根**的 `CLAUDE.md` | 會,而且是**無條件**的(從工作目錄往上找) | 會回來 |
| **子目錄**的 `CLAUDE.md` | 動到那個目錄底下的檔案時,**自動**帶進來 | **不會回來** |
| 本專案的 `docs/` | 只有有人**去查**才會 | 不會回來 |
| agent 記憶 | 由 recall 機制帶入 | 依 recall 機制 |
| **另一個 repo**(跨專案規範、共用規範庫) | **完全不會**——agent 不會無故去讀另一個 repo | 不會回來 |

最後一列是唯一「零自動載入」的:**那一行指路就是唯一的路徑**。它寫壞了,那個 repo 裡的規範等於不存在。

第二列容易被當成第一列,但它們**不是同一件事**:子目錄那份比 `docs/` 自動(不必想到要去查),卻比根那份
不可靠——**規劃階段還沒讀任何檔案時它不在 context,而規劃正是最需要規範的時候**;而且 compact 之後它
不會自己回來,根那份會。

所以規範一旦落在本專案之外,指路要同時滿足三件事:

1. **寫成指令,不是提示。** 「相關規範可參考 X」不會被執行;「先讀 X」會。
2. **觸發條件涵蓋所有會用到的情境——預設是無條件。** 這一條最容易寫錯,而且錯得最安靜:
   「**跨專案時**先讀 X」「**需要時**再看 X」這種限定詞會漏掉主要情境。除非你能舉出「這條規範在
   什麼情況下確定用不到」,否則就寫成無條件的「動任何一個專案之前先讀 X」。
3. **放在會被無條件載入的地方**,也就是上表第一列。指路本身若放進 `docs/` 或另一個 repo,問題只是
   往上搬了一層。

> **語氣對了不代表條件對了。** 實際踩過:指路寫成「開始跨專案的工作之前,先讀 `<規範repo>/CLAUDE.md`」
> ——完全是命令句,第 1 條滿足,但做**單一**專案時不觸發。而那個 repo 裡放的共用登入方式、環境架構、
> 部署慣例,沒有一項只在同時動多個專案時才用得到;其中「所有專案共用同一個登入入口」那條,反而正是
> 只動一個專案時最需要的。

### 一個 repo 裡有多個子專案時:根還是子目錄

上面那張表的前兩列在同一個 repo 內同時存在,而它們的載入行為差很多。所以**在同一個 repo 內**還要再分
一次,判準**不是**「會不會發作」(那一條已經用來分 `CLAUDE.md` 與 `docs/` 了),而是:

> **這條規則會不會在「我還沒打開那個子專案的任何檔案」之前就需要用到?**
>
> 會 → **根**(無條件載入)。不會 → **子目錄**(延遲載入就夠)。

| 規則 | 落點 | 為什麼 |
| --- | --- | --- |
| 某個子專案只能在 64 位元下建置 | **根** | 決定建置參數時就要知道,那時可能一個檔案都還沒讀 |
| 所有站台共用同一個登入入口 | **根** | 任何實機測試都要;不知道會誤判成環境壞掉 |
| 新建某類檔案要存成特定編碼 | 子目錄 | 只有在那個目錄裡建檔時才需要,那時它一定已經載入了 |

**但「不確定就放根」不是安全解。** 實測一個含九個子專案的 repo:九份 `CLAUDE.md` 合計約 1800 行,去掉
重複九次的注入區塊與被複製多份的共通規則之後,根大約落在 900–1100 行——已經接近「規範被稀釋」的邊界。
一份太長的 `CLAUDE.md`,agent 讀是讀了,實際遵守率會下降。所以這條判準是**雙向**的:該放根的放根,
**不該放的堅決留在子目錄**。根長到讓你得捲很久才看得完時,回頭檢查是不是塞了該留在子目錄的東西。

**子目錄那份仍然要叫 `CLAUDE.md`,不要改丟 `docs/`。** 兩者都要「動到才進來」,但子目錄是**自動**的、
`docs/` 要**主動去查**——這個差別足以決定一條規則會不會被遵守。

**把兩層接起來**:上一節那三條指路規則在這裡照樣適用。在**根**寫一條無條件的指令式指路——

> **動任何一個子專案之前,先讀它自己的 `CLAUDE.md`。**

——它同時滿足三條(寫成指令、無條件、放在無條件載入的地方),而且因為它在根,**compact 之後那條指令
還在**,正好補上「子目錄那份不會自己回來」這個洞。

> **指路補得了「不知道要讀」,補不了「讀了不照做」。** 指令在 context 裡,不代表 agent 一定會在動那個
> 子專案之前真的去讀。這是「規範存在」與「規範被執行」之間的差距,沒有任何寫法能關掉它——**真正硬的
> 槓桿是落點本身**:漏掉會出事的規則放根(無條件載入,不依賴任何人記得去讀),指路只負責接住剩下的。

### `docs/` 同一個判準:綁定單一子專案,還是橫跨多個

| 文件性質 | 落點 |
| --- | --- |
| 橫跨多個子專案(工具鏈慣例、發佈流程、跨專案的操作步驟) | **根 `docs/`**,只留一份 |
| 綁定單一子專案(該專案的欄位對照、逐處清單、部署細節) | **子專案 `docs/`** |

**這一格漏掉的實際後果**:實測一個九專案的 repo,一份本質橫向的「套件管理」文件被**複製了三份**放進
三個子專案底下——其中兩份逐行比對**零行不同**,第三份只差一行,而且放在**專案 A** 底下那一份,內文
開頭寫的是**專案 C** 的 solution 檔名。三份各自看起來都正常,只有把它們擺在一起比對才看得出來,而且
**沒有任何東西會報這個錯**。

第二列還有一個容易被忽略的理由:在 SVN 這類**可以只 checkout 子路徑**的版控下,只抓單一子專案的人
拿得到那個專案的 `docs/`,但拿不到根的。專案專屬的文件留在子專案,對他們是實質差別。

### 最上面那張表的第二、三列都落在記憶,分野是「會不會被交接」

記憶**不會跟著 repo 走**——換人、換機器就沒了。所以判準不是「進不進版控」(兩者都不進),而是多問一句:

> **這件事換人接手還需要嗎?**

需要 → 寫成 `type: project`,並在 `MEMORY.md` 留一行索引。不需要 → `feedback` / `user` / `reference`。

交接時跑 **`/tp-export-handover`**,它會把 `project` 那些整理成一份可讀的檔案交出去。**這條路徑必須真的被走過才算數**:記憶沒有匯出過的專案,等於「接手的人需要知道」那一格是空的。

### 不要用一份不進版控的 `TODO.md` 當待辦落點

那個格子——「不進版控、但屬於交接內容」——**沒有任何工具支援**:git 不管它(被 ignore),隔離工作副本只把它帶進去、不搬回來,兩個副本各自加了一條也沒有任何東西能合併。想替它補機制,補出來的每一樣都是在重造 merge(快照=merge base、三態=three-way merge、衝突檔=conflict file)。所以待辦落在記憶,交接靠匯出。

已經有一份**進了版控**的 `TODO.md` 是另一回事:那就是文件,適用上表第一列。

### 被 git 忽略的檔案:三個不變式

隔離工作副本(worktree / 鏡像)對這些檔案**只帶進去,不搬回來**。在副本裡對它們做的任何編輯,副本消失時就跟著沒了,而且**不會有任何警告**。所以放在版控外的檔案必須同時滿足:

1. **不是用來編輯的** — 不要把只存在於那個檔案裡的內容寫進去。
2. **可以重新產生** — 刪掉之後有辦法再生出來(重跑 setup、從範本複製、重新下載)。
3. **可以接受手動編輯** — 使用者手改是預期用法,不會被下一次自動寫入無聲覆蓋。

三條有一條不成立,那份內容就不該待在版控外——它要嘛進版控,要嘛進記憶。
